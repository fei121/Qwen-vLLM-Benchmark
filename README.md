# Qwen3.6-35B-A3B（MoE）与 Qwen3.8-27B（稠密）× RTX PRO 6000

## 一张卡还是两张卡？还是先选对模型？

这是一次面向真实服务决策的 vLLM 推理实验：在完全相同的 300 个请求、20 路并发、4K 输入 / 1K 输出负载下，对比三种配置——**27B 稠密×1 卡、35B-A3B×1 卡、35B-A3B×2 卡**。

![模型与卡数对比](assets/model-comparison.svg)

## 先说结论

这组数据有两层结论，很多人容易只看第二层。

**第一层：同样是单卡，选对模型比加卡更有效。**
- 35B-A3B（约 3B 激活参数）在单卡上把 27B 稠密模型的输出吞吐提升到 **2.16×**；
- 完成时间缩短 **53.7%**，平均 TTFT 降低 **67.2%**，P99 TTFT 降低 **58.0%**；
- 每百万输出 token 的 GPU 时间，35B-A3B 单卡只有 27B 单卡的约 **46%**。

在预算只够一张卡时，激活参数量（而不是总参数量）往往才是单卡吞吐与延迟的主导变量。

**第二层：在 35B-A3B 内部，加卡买来的是容量与尾延迟，不是线性扩展。**
- 输出吞吐从 1,451.64 tok/s 提升到 2,009.36 tok/s，增加 **38.4%**；
- 测试完成时间从 211.62 s 降到 152.88 s，缩短 **27.8%**；
- 平均 TTFT 降低 **56.7%**，P99 TTFT 从 6.28 s 降到 1.85 s；
- 双卡并行效率约 **69.2%**，每百万输出 token 的 GPU 时间反而增加约 **44.5%**。

如果你在意交互式服务的首 token 延迟和尾部体验，加卡值得；如果你在意单位 GPU 成本和单卡产出，**35B-A3B 单卡**才是更高效的基线。

这不是“翻倍加速”的故事，而是**先选对模型、再用加卡换取容量**的双重取舍。

![吞吐与完成时间对比](assets/throughput.svg)

## 这组数据最值得看的地方

平均值只讲了一半故事。

先说 35B-A3B 单卡与双卡的对比。单卡的平均 TTFT 是 535 ms，中位数只有 180 ms，但 P99 达到 6.28 s。大多数请求来得很快，少数请求却会等很久。双卡把 P99 压到 1.85 s，减少了 4.43 s 的长尾；这往往比平均吞吐增加 38% 更能影响用户对系统“快不快”的感受。

再说 27B 稠密单卡。它的平均 TTFT 高达 1,633 ms，**P99 则接近 15 秒**——在并发 20 下，这个尾延迟已经很难支撑交互式服务。而 35B-A3B 即便只跑单卡，P99 TTFT 也只有 6.28 s，比 27B 单卡好上一大截。也就是说，**很多时候问题不在“卡不够”，而在“模型没选对”。**

解码阶段也有类似结论：35B-A3B 单卡的平均 TPOT 是 13.02 ms，27B 单卡是 27.84 ms；给 35B 加第二张卡只是再降到 9.52 ms。收窄“每个 token 间隔”的性价比最高的动作，仍然是先改用稀疏激活模型。

## 一张卡，怎么选？怎么加卡？

**先选模型（单卡预算下）。** 选择激活参数更少的稀疏 MoE（如 `qwen3.6-35b-a3b-fp8`），而不是同预算下的稠密模型（如 `qwen3.8-27b-fp8`）。27B 单卡的 P99 TTFT 约 15 秒，在并发 20 下几乎不具备可接受的交互体验。

**再决定卡数（已确定 35B-A3B）。**
- **单卡**更适合对单位资源产出敏感、容量已够用的场景，或可以通过降低并发来换取更稳定尾延迟；
- **双卡**更适合有明确 P99 SLO、需要更高服务容量、或希望在固定时间内完成更多请求的场景。它购买的主要不是“2 倍速度”，而是更大的吞吐余量和更短的等待长尾。

## 关于这次实验

这是一组单次本地运行结果。当前记录没有包含 vLLM 版本、并行策略、完整启动参数、draft model 与采样参数、GPU 功耗与频率、请求随机种子以及重复试验方差。35B-A3B 为 3B 激活的稀疏 MoE，27B 为稠密模型，二者并非同规模受控对照（未附带模型卡、draft 与采样参数）。因此，本文把结论限定为这几组运行之间的观测差异，不把“换模型”或“加卡”直接归因为因果。

如果要把它升级成容量规划基线，下一步应补充同规模稠密/稀疏模型对照、并发扫描、重复试验、投机解码 on/off 对照、不同输入输出长度，以及 GPU 利用率和跨卡通信数据。
